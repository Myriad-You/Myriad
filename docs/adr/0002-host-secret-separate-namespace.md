# 宿主密钥使用独立的引用命名空间

Status: accepted

TAPP 声明的出站请求可以在请求头、查询串和请求体里引用密钥。应用凭据已经占用了一套模板变量语法。当 TAPP 开始可以引用宿主密钥时，同一处引用就有了两种可能的来源。

决定：宿主密钥使用与应用凭据不同的引用前缀，两者在语法层面就能区分。读 manifest 的人在引用点即可判断这个密钥属于 TAPP 自己还是属于平台，不需要回头对照文件顶部的声明列表。

## Considered Options

**共用同一套语法，靠顶层声明区分来源。** 引用点看不出来源，审计时必须在文件里来回跳；一个 TAPP 可能声明十几个出站端点，逐个对照的负担落在 review 者和管理员身上。同名冲突还需要额外的安装校验规则来兜。

**只支持凭据绑定形式，不做模板变量。** 完全复用现有的静态请求头注入路径，安全边界最清晰，但只能把密钥放进固定请求头。要求密钥放在查询串里的第三方接口就覆盖不到。作为首期缩小范围的切法可行，但契约上要预留模板变量的位置。

## Consequences

宿主密钥的引用可以被静态检出：扫一遍 manifest 就能列全某个 TAPP 用到的平台密钥，这是管理员逐 TAPP 授权界面的数据来源。

代价是模板解析需要认识两套前缀，且两者的解析时机不同——应用凭据按安装解析，宿主密钥按平台配置解析。
