# 升级时 seed 平台配置，消除「库里未设置」态

Status: accepted

平台运行时配置采用「结构体默认值 + 数据库覆盖」的读取方式：库里没有某个 key 时，回落到编译进二进制里的默认值。这带来两个后果。

**升级语义模糊。** 调整任何一项默认值都会连带改变已有站点的行为——旧站升级后可能静默获得新开放的能力。PR #319 正是因此被打回。

**模糊态会放大解析缺失的后果。** AI 配额的六个字段（每日调用数、token 上限、冷却秒数，用户与访客各三项）在配置解析路径里根本没有对应分支。管理员改配额，写库成功，面板回显也正确——因为回显是直接读库的；但真正拦截调用的配额服务拿到的始终是硬编码默认值。权限是布尔值，缺失时回落到关闭至少偏向安全；配额是数值，缺失时回落到一个看起来合理的数字，没有任何异常信号，面板显示的与实际生效的不一致而用户无从察觉。

决定：升级时对全部「管理面板可写」的配置 key 做一次性 seed——库里缺失的，显式写入其**当前旧默认值**落库；之后再调整默认值。范围不限于权限下放开关，AI 配额只是其中一类。

**前置条件**：seed 之前必须先补齐解析。对一个读都不读的 key 做 seed 是纯粹的无用功，值写进去照样被忽略。

## Considered Options

**直接翻转默认值，不做 seed。** 改动最小，但旧站升级即静默扩权。对零成本且可撤销的能力风险确实低，但一旦接受这个模式，将来每一次默认值调整都会重演同样的争论。

**默认值恒为关，改由安装向导为新站落库。** 也能区分新旧站，但安装向导只在建站时跑一次，已建站的实例永远进不到那条路径——产品后续想给旧站开放某项能力时反而无路可走。

**只补解析缺失，不做 seed。** 能修掉配额那个可观测故障，但「库里未设置」这个模糊态原封不动，升级语义问题一次都没解决。

## Consequences

Seed 之后，「库里未设置」被消灭：每个配置项都有明确的落库值。默认值从此是纯产品决策，不再夹带升级语义——这是做这次迁移的主要收益，比任何单次默认值调整都重要。

补齐解析会产生一个需要在升级说明里提示的效果：**此前改过配额但一直未生效的站点，升级后那些设置会突然开始生效。** 这是修复的正确方向，但对管理员而言是行为突变。

代价是配置表会多出数十行显式的默认值，以及需要一个迁移测试证明旧库不因升级扩权。
