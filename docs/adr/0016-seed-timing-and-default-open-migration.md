# seed 走 runtime schema_check，默认开放两项用显式迁移并告知

Status: accepted

ADR 0001 定了「升级时 seed 配置」，但没有定 seed 的时机、幂等实现，以及「默认开放」与「不静默扩权」冲突时谁优先。本决定把这三个空补上。

## 时机与幂等

seed 复用仓库已有的 runtime schema_check（启动时自愈），不是一次性 migration——平台目录 seed 已经在这条路径上跑。幂等采用 `ON CONFLICT (key) DO NOTHING`：库里缺失才写，绝不覆盖站长已经改过的值。

## 默认开放两项是例外

`component:theme` 与 `shortcut:register` 走**显式迁移**，不是「缺失才写」。因为产品批复的是「默认开放」，而「缺失才写」会让旧站永远停在旧默认值（关），产品意图对旧站落空。

这两项与 PR #319 的 40 项全开不同：主题注册、快捷键注册是低风险、可撤销、可感知的能力，不涉及泄露面、破坏面、消耗面；`component:theme` 还有 ADR 0008 兜底（只有安装 owner 能注册，guest 拿不到）。「不静默扩权」的正确解法不是不做，是做并**明确告知**：升级说明里单列这两项，说明升级后普通用户默认获得主题组件注册与快捷键注册。

## Consequences

配置 seed 分两类：

| 类 | 字段 | 方式 |
|-|-|-|
| 默认开放 | `component:theme`、`shortcut:register` | 显式迁移写「开」 + 升级说明单列告知 |
| 其余全部 | AI 配额 6 字段、暂存阈值 4 字段等 | `ON CONFLICT DO NOTHING`，缺失才写默认值 |

显式迁移写「开」必须同时满足：不覆盖「站长曾显式设过关」的值。因为旧站库里这两个 key 可能是旧默认值（seed 进去的）也可能是站长手动设的，迁移实现需要能区分两者——否则会把站长明确关闭的能力重新打开，那才是真正的静默扩权。

**时序约束：显式迁移必须早于 seed 执行。** seed 用 `ON CONFLICT DO NOTHING` 把缺失的 key 写入旧默认值（关）。如果 seed 先跑，`component:theme` / `shortcut:register` 就会被写成「关」，此后「站长显式设过关」与「seed 写入的旧默认值关」在库里的表示完全一致，区分两者的信息已被不可逆地抹掉——显式迁移再也无法只对「从未被站长触碰过的站」写「开」，反而会把站长明确关闭的站重新打开。因此这两项的显式迁移必须**在 seed 之前**完成判断：此时「库里有值」等价于「站长设过值」，才可能做到「不覆盖显式关闭」。这个顺序不是实现偏好，是「默认开放」与「不静默扩权」两条约束能够同时成立的前提。
