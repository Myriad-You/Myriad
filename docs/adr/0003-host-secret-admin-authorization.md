# 宿主密钥由管理员逐应用授权，默认拒绝

Status: accepted

宿主密钥属于平台，不属于任何一次安装。让 TAPP 借用它，实质是让多个来源不明的应用共用同一份凭据——风险不在于某个 TAPP 是否诚实，而在于共用本身：其中一个把配额烧光或触发第三方限流，受影响的是平台自己的数据同步，且事后无法定位是谁干的。

决定：借用宿主密钥需要管理员针对「哪个应用、借用哪个密钥」逐项授权，未授权即拒绝。授权可以随时单独撤销，不影响其他应用。

## Considered Options

**安装时由安装者确认，管理员事后撤销。** 在个人平台上安装者通常就是站长，看似与管理员授权等价；但一旦访客或次级用户能安装应用，就等于让非管理员支配管理员的凭据。这个口子不该开。

**按密钥设总开关，不区分应用。** 粒度太粗：一个开关对所有声明了该密钥的应用生效，出问题时既无法定位来源，也无法只关停单个应用。

## Consequences

普通用户安装后可能撞墙——应用需要平台凭据但尚未获批。为了让撞墙撞得明白，声明了宿主密钥的应用必须同时声明降级行为：拿不到凭据时是完全不可用，还是退化成受限模式。

授权关系需要独立记录，不能挂在安装记录上：应用更新、重装都不应静默继承或丢失授权，而密钥值的变更也不应触发重新授权——变的是值，授权针对的是「谁可以用哪个密钥」这层关系。
