# 平台配置的读写一致性由测试保证

Status: accepted

平台运行时配置从数据库读回内存时，每个字段都对应一段手写的取值分支。加字段时忘记补这段分支，编译器不会报错，也不会崩溃——配置只是永远不生效。AI 配额的六个字段就是这样漏掉的，且面板回显直接读库，所以显示正确、实际无效，管理员无从察觉。

决定：加一个一致性测试，断言配置结构体的每个字段都在解析路径里出现过；确实不该从库里读的字段列入豁免清单，每项须写明理由。漏字段从一个线上静默故障变成一次 CI 红灯。

## Considered Options

**只补当前漏掉的字段，不动结构。** 改动最小，但同样的漏下次还会出现——而接下来要新增宿主密钥授权关系、常驻名额上限等一批新配置项，正是高发期。

**改成由结构体定义派生解析。** 从根上消除「手写一段」这个环节，但现有解析里有相当一部分不是简单的一对一映射：敏感值要解密、部分字段是嵌套结构、部分做过类型兼容处理。这些特例需要另找地方安置，改动面远超本次范围。

## Consequences

这不是引入新做法。仓库里已有同类实践——生成的命令行契约不得放行后端禁止的请求头、前后端权限表必须一致，都由测试断言。本次只是把既有模式补到漏掉的地方。

豁免清单需要判断力，且会随时间腐化：某个字段后来改成该读了，却忘了从清单里删除。要求每项写明理由是唯一的缓解手段。

注意此测试与 TAPP 清单契约的生成链路无关。那条链路的方向是「后端导出真相供外部工具校验开发者写的清单」，而这里要解决的是平台自身配置读写两侧的一致，不需要向任何外部工具导出。
