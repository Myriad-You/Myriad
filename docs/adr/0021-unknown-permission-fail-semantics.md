# 运行时权限过滤遇到未知权限名：签发路径失败、展示路径标记

Status: accepted

ADR 0013 只立了一条原则——「未知权限名必须显式失败，不得静默丢弃」——但没定失败在各调用路径上的具体形态。`filter_permissions_for_role`（`backend/src/services/permission_service.rs:413`）当前用 `filter_map` 把不认识的名字直接丢掉，是唯一的静默丢弃点。删旧枚举前必须把它改成显式，否则已装老应用升级后会在不报任何错误的情况下少掉能力。

决定：把 `filter_permissions_for_role` 的调用点分成两类，失败语义不同。

**签发路径（fail-closed）**：Runtime Grant 的签发与校验、安装时的批准权限计算、资源创建。这几处对未知权限名的正确反应是**整个操作失败**——不签发一份缺斤少两的 grant，不落库一份悄悄少权限的安装。调用点：`tapp_runtime_grant.rs:272`（签发 + 校验）、`runtime_grant.rs:194`（签发）、`access.rs:165`（安装批准计算）、`resource_create.rs:71`（资源创建）。

**展示路径（fail-soft）**：目录列表里计算某个应用「当前授予哪些权限」用于展示（`tapp_catalog.rs:172`）。这里失败不能把整个列表页打挂，但也不能静默丢弃——应把该应用呈现为 ADR 0018 定义的「需重新授权」状态，让站长看到「此应用权限已过期，需处理」。

## Considered Options

**全部 fail-closed。** 语义最简单，但展示路径一个坏权限就能让目录列表整体报错，站长连「哪个应用坏了」都看不到，也无法在界面上发起重新授权。

**全部沿用 filter_map 静默丢弃。** 就是现状，也是 ADR 0001 / 0004 要消灭的那类静默失败，直接否掉。

**签发失败、展示标记。** 本决定。签发路径本来就该在授权前提不成立时拒绝；展示路径需要的是「可看见、可操作」，而不是「能算出正确权限」——坏权限串本来也算不出正确权限。

## Consequences

函数签名需能区分两类调用方。手段属于实现层：可以是让 `filter_permissions_for_role` 返回 `Result` 而展示路径捕获错误转成「需重新授权」标记，也可以是保留一个展示用的宽松变体。约束只有两条：签发路径不得返回「丢弃了未知项的结果」，展示路径不得因未知项崩溃。

未知权限名进入运行时过滤路径的来源，正常情况下只有「旧枚举已删、库里还存着旧权限串」这一种——即 ADR 0018 迁移要清除的存量。签发路径的 fail-closed 与 0018 的「清空 + 标记需重新授权」是同一件事的两道闸：迁移没清干净的，运行时拒掉而不是放行。
