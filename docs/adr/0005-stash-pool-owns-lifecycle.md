# 暂存池统一管理离场实例，运行与否是池内属性

Status: accepted
Note: 首段的事实描述被 ADR 0014 更正——`lifecycle:pause` / `lifecycle:resume` 已经存在，切 Tab 与窗口最小化走的是保留沙箱的路径。真实缺口是小组件离屏与数据刷新这两条路径未接线。本 ADR 的结论不变；文中「暂存」一律按 ADR 0014 的「隐藏」读。

平台今天对小组件沙箱只有「活着」和「销毁」两种状态，而触发销毁的条件里混进了大量非破坏性事件：滚出视野、切换页面、布局重排。应用因此分不清「用户不看我了」和「用户不要我了」，只能每次都当成后者——用户滚回来看到的是重建后的空白实例。

另一方面平台已有「后台常驻」这一概念：应用可声明自己在不可见时仍需运行（典型场景是音乐播放）。它与暂存形状相似但意图相反——常驻是应用要求「别停下我」，暂存是平台决定「先留着你但让你停下」。

决定：所有离场实例都进暂存池，由池统一负责容量、淘汰与清理；**实例是否继续运行是池内的一个属性**，由常驻资格决定，而不是另一条绕过池的独立通道。

## Considered Options

**常驻实例不进池，保持原样活跃。** 两个机制各管各的，边界按声明划。问题是常驻实例完全游离在容量控制之外——声明了常驻的应用可以无限累积实例，池辛苦设的上限对它无效，这是可被滥用的口子。

**全部进池并一律停止，常驻声明只影响淘汰顺序。** 语义最统一，但抹掉了常驻的核心诉求：进池就得停，声明失去意义，音乐会断。

## Consequences

池要同时持有两类实例，淘汰策略必须区别对待——这是 ADR 0006 的主题。

暂存的实例仍持有授予权限与会话令牌。长时间暂存后恢复时，授权前提可能已经变化（配置被改、令牌过期），恢复路径必须重新确认，不能假设暂存期间世界静止。销毁路径不存在这个问题，因为重建时会完整走一遍授权。

「看不见却活着」需要一个可见的出口：用户应当能看到当前有哪些实例在后台存活并单独停掉它们。浏览器在标签页上放小喇叭是同一个道理——否则遇到耗电、发热或莫名的声音时用户无从下手。
