# TAPP 能力放宽：愿景与用户故事

> 本文档回答「为什么做这件事」，面向需求理解，不涉及实现与架构。
> 实现层面的决策见 [`docs/adr/`](../adr/)；术语见仓库根 [`CONTEXT.md`](../../CONTEXT.md)。

## 一句话愿景

Myriad 是一个个人数字生活平台——一个人可以搭起自己的小宇宙，往里面装各种小应用（TAPP），像搭积木一样拼出自己想要的首页、阅读器、播放器、数据看板。TAPP 是这些积木，由开发者在沙箱里写好、打包上传，用户装上就能用。

「权限放宽」要回答的问题是：**这些积木到底能被允许做多少事，才能既好用、又不失控。**

## 三个痛点

**痛点一：能力要么全给，要么全不给。**
一个应用想「读订阅」做阅读统计，但现在的能力是一整块的——给了它读，往往连「删订阅」「改数据」也一起给了。开发者要么被捆住手脚，要么一放开就什么都能碰。没有「恰到好处」。

**痛点二：小组件滚出屏幕就没了。**
用户在首页的待办清单里打字，临时滚下去看篇文章，再滚回来——那个小组件被销毁重建了，打了一半的字全没了，还闪一下空白。用户分不清「我只是暂时没看你」和「我彻底不要你了」。

**痛点三：想接第三方服务，密钥是个死结。**
开发者想做个 GitHub 看板、天气卡片，这些服务需要 token。token 写进应用里，装上的人就能在沙箱里翻出来，泄漏了；不写进去，应用又用不了。接第三方这件事卡死了。

## 三个转变

1. **从「一授全开」到「按风险分级的细粒度能力」**——把能力拆细，每个能力按「会不会泄露数据、会不会改坏东西、会不会烧钱」定级，能隔离、能限流、用户看得见可撤销的才放开。
2. **从「销毁重建」到「暂存恢复」**——小组件只是「暂时离开」，回来还是原来那个；只有真正的卸载、登录态变化、代码更新才销毁。
3. **从「密钥进沙箱」到「密钥只写、平台代用」**——密钥存在平台侧，应用只声明「我要用 GitHub」，平台在宿主后端把密钥放进发往 GitHub 的请求头，密钥从头到尾不落到应用手里。

## 五个用户故事

### 故事一：访客只能「住」，不能「装修」

站长小川给站点定了一套「暖纸蓝调」主题。访客路人甲打开站点，看到的就是这套主题——他能享受，但没资格改，更没资格往站长的主题列表里塞自己的一套。主题是站长的装修，访客只能住、不能动。

### 故事二：滚回来，字还在

用户小明在首页的待办清单里打字，临时滚下去看文章，再滚回来——希望还是他那个清单，字还在，就像切到后台又切回来，而不是被关掉重开。音乐播放器也是同一个诉求：切页时歌不要断。

### 故事三：应用接 GitHub，开发者不碰 token

开发者老李写了个 GitHub 看板，要显示仓库 issue。GitHub 要 token。老李的理想是：token 存在站长那里、只能写不能读回；他的应用只声明「我要用 GitHub 这个 key」，平台在宿主后端把 token 注入请求头并替它调用。token 从头到尾不在应用手里。

### 故事四：站长对「后台活着的东西」有掌控感

小川装了音乐播放器，希望切页时音乐不断。但某天他发现手机发热、有莫名声音，却不知道是哪个应用在后台偷偷跑。他希望像浏览器标签页上的「小喇叭」图标一样——一眼看到「现在有哪些应用在后台活着」，点一下就能单独停掉。

### 故事五：应用申请的是「最小够用」的那一块

老李想让应用「读订阅」做统计，但绝不想要「删订阅」的能力。理想是：读是低风险、可以直接给；写要加护栏（限流、审核）；删只有站长才给。应用只申请它真正需要的那一小块，而不是被迫全要或全不要。

## 这件事最终要达成的样子

开发者写一个 TAPP，能用自然的方式说清楚「我要读这些、写这些、定时做这些、接这个第三方」；站长装上它时，一眼看懂它要什么、给到什么程度、哪些要自己点头；用户用起来时，滚进滚出不丢状态、后台有什么在跑心里有数；而密钥这种最敏感的东西，永远不落到应用手里。

这三类人——**开发者、站长、用户**——各得其所，同时没有一方能越界。这就是「权限放宽到最大安全边界」这句话真正想说的意思。
